# Android 16 hardware — what one unstable cloud device did and did not verify

2026-11-03. A Samsung **SM-S948B** reached over a cloud ADB tunnel (`rdb`, a local port
that adb connects to). The run was abandoned partway because the tunnel would not stay up;
this records the two things that completed, and everything that did not, so the next
session does not have to guess which.

## The device

```
ro.product.model                 SM-S948B
ro.product.manufacturer          samsung
ro.product.device                m3q
ro.build.version.release         16
ro.build.version.sdk             36
ro.build.version.security_patch  2026-08-05
ro.build.fingerprint   samsung/m3qxser/m3q:16/BP4A.251205.006/S948BXXS4AZHL_OXM4AZHL:user/release-keys
ro.product.cpu.abilist           arm64-v8a
ro.soc.manufacturer              QTI
ro.soc.model                     SM8850
ro.board.platform                canoe
getconf PAGE_SIZE                4096
nproc                            8
id -u                            2000
```

**It closes one gap and not the two it looks like it closes.** This project had no Android
16 hardware at all, only emulators, and now it has touched some. It does **not** close the
16 KB page gap — `PAGE_SIZE` is 4096 — and it does **not** close the non-Qualcomm gap: SM8850
is a Snapdragon. Anyone reading "Android 16 flagship" and assuming three gaps closed at once
would be wrong on two of them.

`id -u` is 2000, so there is **no root**, and that rules out L2, L3 and L4 by more than
inconvenience: `lockClocks` needs root, L3 and L4 write the app's preferences into
`/data/data`, and `BENCHMARKS.md` §10.6 turns an unlocked-clock run into `inconclusive`
*by rule*. A benchmark run here would have produced a result file that cannot be compared
with anything.

## What completed

| Check | Result |
| --- | --- |
| The minified `benchmark` APK installs | `Performing Streamed Install` / `Success` |
| `CaptureActivity` starts | started; a screenshot was captured |
| **21 `:scanner` instrumentation tests** | **`OK (21 tests)`, `INSTRUMENTATION_CODE: -1`, 21 passed / 0 failed** |

The instrumentation result is the one worth having. It is a single self-contained
`am instrument -w -r` that either completes or does not, so a flapping link cannot turn a
failure into a pass; and the 21 include the **12 native-decoder tests**, so `zxing-cpp`
builds, loads and decodes correctly on arm64 Android 16 on an SM8850. Until now every
Android 16 claim in this repository came from an emulator.

## What did not complete, and is therefore not claimed

- `libzxingnative.so` being present in the process's own `/proc/<pid>/maps` — the pid read
  came back empty on the attempt that ran, so the process-level checks were skipped rather
  than guessed at.
- Camera service state, whether frames reach the decoder, the thread list, the 100-cycle
  open/close loop.
- Anything about the camera at all. The device is in a datacentre; there is no scene.
- L1 over the corpus. It pushes 109 MB and this link could not be trusted with it.

## The trap, because it cost the first whole run

`tools/maint/android16-checks.sh` retries every command. Its first version retried by
calling `adb connect` — and **`adb connect` does not repair a transport that has gone
`offline`**. It answers `already connected` and leaves the dead transport in place. So the
retry loop tried the same broken connection five times per step and reported a working
device as unreachable, failing all 34 steps in a row. The fix is `adb disconnect` *then*
`adb connect`; with it, eight consecutive probes succeeded where zero had before.

Second, smaller: a failed `pidof` returned the literal string `FAILED`, which was then
interpolated into `/proc/FAILED/maps` and into an `unbound variable` error. The script now
treats a non-numeric pid as "no process" and skips what depends on it.
