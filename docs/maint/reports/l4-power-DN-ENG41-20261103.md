# Does CameraX's extra CPU cost battery? — DN-ENG41, 2026-11-03

The question the Phase 6 decision record could not answer, and the reason the CameraX
default had not moved: L4 measured CameraX at ~60% more CPU to keep scanning, and the
baseline soaks were on charge, so `l4-verdict-DN-ENG41-20261102.md` records power as **not
measured**. This run tried to measure it.

Two 12-minute soaks, one per backend, back to back in one session, miss path, clocks not
locked (L4 does not lock them), thermal status 3 throughout — the same conditions the
baseline records. Commit `aff9b8105`. Result files:
`l4-{camera1,camerax}-DN-ENG41-20261103-power.json`.

## The CPU finding reproduces, on a different day and a changed codebase

| | camera1 | camerax | baseline 2026-11-02 |
| --- | --- | --- | --- |
| CPU, % of one core | **78.8** [73.4–87.6] | **123.6** [113.3–133.5] | 74 / 118 |
| Total PSS | 64,022 kB | 79,206 kB | 61,136 / 77,731 |
| Threads | 27.5 | 44.0 | 27 / 44 |

**+57%**, against the baseline's +59%. Every column lands where the baseline put it, which
also says the Camera1 async-open change did not move steady-state cost — it was a startup
change and it stayed one.

## The power answer is "this device cannot tell", and that is a result

DN-ENG41 cannot be made to discharge: there is no `input_suspend`, `charging_enabled` or
equivalent anywhere under `/sys/class/power_supply`, the battery sits at `Full` / 100%, and
`battery/current_now` reads 0. So the fuel gauge is flat by construction and
`battery_drain_ma` is null with a `NOT_DISCHARGING` warning.

What is measurable is the **USB input current times its voltage**: a full battery taking no
charge draws nothing, so what comes in at the port is what the phone is using. Screen
brightness was pinned to 128 with auto-brightness off in both arms, because it dominates
this number.

```
camera1   3211 mW   (sd 510, n = 22)
camerax   3226 mW   (sd 486, n = 21)

camerax - camera1 = +15 mW,  95% CI [-272, +308] mW
                  = +0.5%,   95% CI [-8.5%, +9.6%]
```

Bootstrap, 20,000 resamples, seed 20261102 — §7's method.

**The interval straddles zero and is wide.** Per-sample values run 2346–4172 mW on one arm
and 2448–4384 on the other, and the two halves of each soak drift in *opposite* directions
(camera1 3322 → 3099, camerax 3064 → 3372). A series dominated by the backend under test
would not do that; this one is dominated by the charger's own behaviour and the screen.

So the honest reading is **not** "the two backends cost the same power". It is: *this
measurement has no power to resolve the difference.* What it does give is a bound — the
whole-device difference is smaller than about 300 mW. For scale, CameraX's extra ~0.45 of a
core at a rough 300–500 mW for a busy big core is 150–250 mW, which sits **inside** that
interval. The instrument is not sensitive enough to see a difference that ought to be there.

Settling it needs a device that can actually discharge, and then the fuel gauge
(`charge_counter`) does the work without any of this reasoning. The harness samples it
already.

## What this does to the default

Three arguments have been weighed against making CameraX the default. After today:

| | Before | Now |
| --- | --- | --- |
| Coverage | CameraX unverified on a second device | answered — two phones, two Android versions, R8, a real decode |
| Startup latency | CameraX ~330 ms faster to a drawn window | **reversed** — Camera1 is now 291–360 ms faster (`l3-async-open-DN-ENG41-20261103.md`) |
| Steady-state cost | +60% CPU, power unmeasured | **+57% CPU, reproduced; power unresolvable here, bounded at ±300 mW** |

Every performance argument that once favoured CameraX has either reversed or turned out to
be unmeasurable on the available hardware. The single measurable difference left says
CameraX is more expensive.

**Recommendation: leave the default at `CAMERA1`.** Not because CameraX is bad — the
maintenance and deprecation case in `decisions/0001-camera-backend.md` stands untouched, and
CameraX remains one line away for any caller — but because moving a shipping default
towards the only measurably more expensive path needs a reason, and there is no longer one
on the table. The maintenance argument is about *whether to keep maintaining Camera1*, which
is a separate decision; today's work is the evidence for keeping them separate, since the
one real defect found was fixed **on the default path** rather than stepped around by
switching away from it.

## Not measured

- **The hit path.** Miss path only, as §12.3 specifies.
- **Any other device.** One phone, permanently at thermal status 3.
- **Where CameraX's extra CPU goes.** Needs a profiler; the harness only counts it.
