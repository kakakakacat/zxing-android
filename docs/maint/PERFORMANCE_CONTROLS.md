# Experimental scanning controls / 实验性扫描性能控制

These controls are opt-in and carry no measured speedup claim. The default camera,
decoder, ROI and allocation path are unchanged. Change one variable per A/B run.
这些控制项均需显式启用，不代表已测得加速；默认相机、解码器、ROI 和分配路径保持不变。
每次 A/B 只修改一个变量。

```kotlin
val options = ScannerOptions.Builder()
    .setCameraBackend(ScannerOptions.CameraBackend.CAMERAX)
    .setPreviewSize(1280, 720)
    .setAnalysisSize(640, 360)
    .setProgressiveRoi(true)
    .setJavaBufferReuse(true)
    .build()
```

| Control / 控制项 | Contract / 行为约定 |
| --- | --- |
| Analysis size / 分析尺寸 | CameraX requests it separately from preview; 0/0 follows preview. Requested and negotiated stream aspect ratios must agree. Actual resolutions are logged and can differ from requests. Camera1 logs that this setting is ignored because it has one shared stream. / CameraX 独立请求分析尺寸；0/0 跟随预览。请求及协商后的宽高比须一致。日志记录实际尺寸，可能与请求不同。Camera1 只有一个共享流，会记录忽略此选项。 |
| Progressive ROI / 渐进式 ROI | One decode per frame: two attempts at half width/height, two at three quarters, then one over the complete configured scan rectangle. Never expands beyond the host rectangle. Success, format changes and size changes reset the cycle. Sources without crop support use the whole rectangle. / 每帧一次解码：半宽半高两次、四分之三宽高两次、完整取景框一次；不越过宿主取景范围。成功、码制及尺寸变化后重置；不支持裁剪的输入使用完整区域。 |
| Coordinates / 坐标 | Result points and candidate callbacks are offset back to the original scan region. Result payload, bits, metadata and timestamp are preserved; thumbnails still show the original scan region. / 结果点和候选点还原到原始取景区域；保留内容、位数、元数据及时间戳；缩略图仍使用原始取景区域。 |
| Java buffer reuse / Java 缓冲区复用 | A decoder owns one exact-size matrix scratch for Y-plane input and replaces it on area changes. Copying remains lazy so 1D readers need not copy a matrix. Public getMatrix() returns independent arrays; scratch is released on close. Threshold arrays and BitMatrix are not reused. / 解码器独占一个与 Y 平面 ROI 面积匹配的矩阵缓冲区，面积变化时替换。延迟复制保留一维码按行读取路径。公开 getMatrix() 仍返回独立数组，关闭时释放工作区；本次不复用阈值数组和 BitMatrix。 |

## Reproduce / 复现

Use the existing locked-device procedure in [BENCHMARKS.md](BENCHMARKS.md). Select
only the named class so stages do not get mixed. Each backend runs in a separate process.
沿用 [BENCHMARKS.md](BENCHMARKS.md) 的锁频真机流程，仅选择指定测试类，避免混入其他阶段。
每个 backend 独立进程运行。

```sh
# Repeat with java-reuse to compare Java ROI matrix reuse on direct Y-plane input.
# 改为 java-reuse 再运行一次，对比 direct Y 平面输入下的 Java 矩阵复用。
./gradlew :benchmark-android:connectedReleaseAndroidTest   -Pandroid.testInstrumentationRunnerArguments.class=io.github.kakakakacat.zxing.benchmark.DirectPlaneBenchmark   -Pandroid.testInstrumentationRunnerArguments.l2.backend=java   -Pandroid.testInstrumentationRunnerArguments.l2.matrix=full

# Repeat with java-progressive, native, native-progressive and format-aware.
# 分别换用 java-progressive、native、native-progressive、format-aware。
./gradlew :benchmark-android:connectedReleaseAndroidTest   -Pandroid.testInstrumentationRunnerArguments.class=io.github.kakakakacat.zxing.benchmark.FrameSessionBenchmark   -Pandroid.testInstrumentationRunnerArguments.l2.backend=java   -Pandroid.testInstrumentationRunnerArguments.l2.matrix=full
```

`directPlaneEndToEnd` keeps pixels and ROI identical. The ordinary `java` run also
includes the one-cursor-per-matrix implementation, so this A/B isolates matrix reuse.
`native` versus `native-direct` continues to measure the direct JNI input path.
`directPlaneEndToEnd` 保持图像和 ROI 一致；普通 java 路径也包含每矩阵一个游标的实现，因此 A/B
仅比较矩阵复用。native 与 native-direct 继续用于直接 JNI 输入对比。

`sessionEndToEnd` resets formats (included in timing), replays two MISS frames, then up
to five identical target frames and stops on success. It checks final results against
Java before timing. This is decoder CPU replay cost, not wall-clock first-scan latency;
it excludes camera delivery, frame pacing, autofocus, power and thermal effects. The
existing golden hashes identify the target pixels; the MISS prelude is generated by the
same golden-tested frame factory. Progressive backends belong in this session benchmark,
not the existing single-frame benchmark whose first attempt must already match Java.
`sessionEndToEnd` 将码制配置重置计入耗时，先回放两帧 MISS，再最多五帧相同目标图像，成功即停止；
计时前对比 Java 的最终结果。这是解码 CPU 回放成本，不是实际首次扫码延迟，不包含相机送帧、
请求间隔、对焦、功耗和温控。现有 golden 标识目标图像；MISS 前序帧由相同的 golden 测试生成器生成。
渐进式 backend 应运行会话基准，不能用于要求首帧结果即与 Java 一致的原有单帧基准。

## Acceptance / 验收

Before changing defaults, measure camera-to-result P50/P95, timeout/misread rates,
allocated bytes/GC, CPU time and sustained temperature/power on physical devices.
Include center/edge, small/distant, low-light and moving symbols. A reduced analysis
resolution may lose small symbols; progressive ROI may delay edge symbols by four
attempts. Neither tradeoff is established by emulator success or replay speed alone.
修改默认策略前，需真机记录从相机到结果的 P50/P95、超时及误识别率、分配/GC、CPU 时间及持续温度/功耗。
覆盖中心/边缘、小码/远距、弱光和运动场景。降低分析分辨率可能漏掉小码，渐进 ROI 可能让边缘码多等四次尝试。
模拟器通过或回放变快都不能单独证明这些取舍可接受。
